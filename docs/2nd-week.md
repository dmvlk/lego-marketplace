# Вторая неделя: инфраструктура

## Результат этапа

Подготовлено базовое окружение для локальной разработки. Запуск инфраструктуры выполняется через Docker Compose. Добавлена единая точка входа API Gateway.

Проверено в Docker:

- все основные контейнеры находятся в состоянии `healthy`;
- Gateway отвечает на `/api/v1/health`;
- LocalStack сообщает, что сервис S3 доступен;
- PostgreSQL содержит все семь изолированных баз сервисов;
- конфигурация проходит `docker compose config --quiet`

## Состав Docker Compose

- PostgreSQL 16 - реляционные данные
- RabbitMQ 3 с management-интерфейсом - доменные события
- Redis 7 - кеширование, временное состояние и ограничение частоты запросов
- LocalStack с сервисом S3 - совместимое с S3 хранилище изображений
- API Gateway на FastAPI - публичная точка входа

PostgreSQL при первом запуске создаёт изолированные логические базы:

- `auth_db`
- `catalog_db`
- `deals_db`
- `payment_db`
- `delivery_db`
- `chat_db`
- `reviews_db`

Микросервисы не будут обращаться к чужим базам и будут использовать только собственные базы или схемы.

## Структура Gateway

```text
backend/gateway/
├── app/
│   ├── __init__.py
│   └── main.py
├── Dockerfile
└── requirements.txt
```

Gateway предоставляет базовые health-эндпоинты:

- `GET /api/v1/health`
- `GET /api/v1`

В данном этапе Gateway не содержит маршруты бизнес-сервисов: они будут добавляться по мере создания сервисов.

## Переменные окружения

Файл `.env.example` содержит необходимые настройки PostgreSQL, RabbitMQ, Redis, LocalStack и JWT. Реальные секреты не добавляются в репозиторий.

Перед запуском можно создать рабочий файл окружения:

```powershell
Copy-Item .env.example .env
```

## Запуск

```powershell
docker compose up --build -d
docker compose ps
```

Проверить Gateway:

```powershell
curl http://localhost:8000/api/v1/health
```

Проверить веб-интерфейсы инфраструктуры:

- RabbitMQ: `http://localhost:15672`
- S3 endpoint: `http://localhost:4566`

## Проверка остановки и перезапуска

```powershell
docker compose down
docker compose up -d
docker compose ps
```

Данные PostgreSQL, RabbitMQ, Redis и LocalStack сохраняются в Docker volumes.

## Частичный результат этапа 3: сервис авторизации

Реализован независимый сервис `auth-service`:

- отдельный Dockerfile и Alembic-миграции;
- база `auth_db`;
- модели ролей, пользователей и refresh-токенов;
- регистрация и вход;
- хеширование паролей Argon2;
- access-токены JWT и ротация refresh-токенов;
- получение и изменение собственного профиля;
- выход и отзыв refresh-токена;

Сервис доступен внутри Compose на порту `8001`, а публичные routes Gateway доступны через `/api/v1`.

Проверенные HTTP-сценарии:

- регистрация пользователя;
- вход по email и паролю;
- получение профиля с access-токеном;
- обновление профиля;
- ротация refresh-токена;
- повторное использование старого refresh-токена отклоняется;
- выход отзывает refresh-токен;
- маршрутизация через Gateway на порту `8000`

## Сервис сделок

Добавлен независимый `deals-service` с базой `deals_db`:

- отдельные сущности сделок, предложений, снимков объявления и истории статусов;
- REST-запросы к каталогу и внутренний сервисный токен;
- атомарное резервирование объявления с защитой от конкурентной покупки;
- предложения и встречные предложения без перезаписи истории;
- офлайн-сделка завершается только после подтверждения покупателя и продавца;
- отмена до завершения освобождает объявление;
- покупки и продажи видны только участникам сделок;
- снимок сохраняет описание, цену, состояние, комплектность и изображения

`ONLINE_PROTECTED` пока создает сделку в состоянии `AWAITING_PAYMENT`. Платежи, доставка, споры и события RabbitMQ будут подключены отдельными этапами. Это состояние не означает, что деньги приняты или удерживаются.

Проверены переговоры, офлайн-завершение, отмена, отказ второй параллельной покупки и запрет доступа третьего пользователя. Использованные для HTTP-проверки аккаунты и объявления удалены; тестовые записи не остаются в БД.

## Платежный сервис

Добавлен `payment-service` с отдельной базой `payment_db` и демонстрационным Mock-провайдером. Реальные списания и переводы не выполняются.

- запуск платежа доступен покупателю защищенной онлайн-сделки;
- комиссия составляет 5% и вычитается из выплаты продавцу;
- платежи, возвраты, выплаты и события провайдера сохраняются отдельно;
- повторная обработка вебхука защищена подписью и идемпотентностью;
- авторизация Mock-платежа переводит сделку в `PAID`;
- операции возврата и выплаты доступны сервисам через закрытые внутренние маршруты

Публичные маршруты: `POST /api/v1/payments/deals/{deal_id}`, `POST /api/v1/payments/webhooks/{provider}` и `GET /api/v1/payments/{payment_id}`. Автоматическая выплата после доставки и инспекционного периода подключена через сервис сделок.

## Сервис доставки

Добавлен `delivery-service` с отдельной базой `delivery_db`. Продавец создает отправление для оплаченной онлайн-сделки, добавляет трек-номер и вручную обновляет статусы mock-доставки. История отслеживания сохраняется в базе; данные доступны только участникам сделки.

После подтверждения доставки сделка переходит в `INSPECTION` на 48 часов. Покупатель может подтвердить получение раньше; по истечении срока сделка завершается автоматически. Выплата отправляется через идемпотентную очередь в базе сделок с повторами после ошибок, поэтому незавершенная задача сохраняется при перезапуске.

Публичные маршруты: `POST /api/v1/deliveries/deals/{deal_id}/ship`, `GET /api/v1/deliveries/deals/{deal_id}`, `PATCH /api/v1/deliveries/{shipment_id}/tracking`, `POST /api/v1/deliveries/{shipment_id}/delivered` и `POST /api/v1/deals/{deal_id}/inspection/confirm`. Автоматическое завершение учитывает только сделки в состоянии `INSPECTION`; спорный статус блокирует выплату.

## Сервис чатов

Добавлен `chat-service` с отдельной базой `chat_db`. Покупатель открывает приватный диалог с продавцом по активному объявлению; повторный запрос возвращает тот же диалог. История сообщений хранится в базе, количество непрочитанных сообщений рассчитывается отдельно для каждого участника. Проверка участия выполняется и для REST-запросов, и для WebSocket.

Сообщения можно отправлять через REST или WebSocket `/api/v1/ws/conversations/{conversation_id}`. WebSocket проходит через Gateway; при подключении клиент передает access-токен первым сообщением в формате `{"type":"authenticate","access_token":"..."}`.

## Споры по защищенным сделкам

Покупатель может открыть один спор по защищенной сделке в статусе `PAID`, `SHIPPED` или `INSPECTION`. Сделка переходит в `DISPUTED`, поэтому инспекционный worker не завершает ее автоматически. Продавцу отводится два рабочих дня на ответ; по истечении срока спор передается на рассмотрение без автоматической победы любой стороны.

Участники могут добавлять текст, выдержки переписки, сведения о трекинге и изображения. Изображения проверяются по формату и размеру и сохраняются в S3; просмотр доступен только участникам и администраторам. Администратор может запросить дополнительные доказательства у любой стороны, также установив срок в два рабочих дня.

Администратор выбирает полный возврат, выплату продавцу или частичный возврат. Решение и действия администратора сохраняются в аудите. Возврат и выплата выполняются через закрытые API платежного сервиса и долговечную очередь с идемпотентными ключами; частичный возврат выполняется до выплаты остатка. Роль `ADMIN` не выдается публичной регистрацией: ее назначают существующему пользователю отдельно, после чего нужно получить новый access-токен.

Публичные маршруты: `POST /api/v1/deals/{deal_id}/disputes`, `GET /api/v1/disputes/{dispute_id}`, `POST /api/v1/disputes/{dispute_id}/evidence`, `POST /api/v1/disputes/{dispute_id}/evidence/images`, `GET /api/v1/admin/disputes`, `POST /api/v1/admin/disputes/{dispute_id}/request-evidence` и `POST /api/v1/admin/disputes/{dispute_id}/resolve`.

## Сервис отзывов

Добавлен `reviews-service` с отдельной базой `reviews_db`. Отзыв доступен только покупателю завершенной сделки после закрытия спора, если он был. Ограничение уникальности в БД не позволяет оставить более одного отзыва по сделке. Оценка принимает значения от 1 до 5, текстовый комментарий необязателен.

Публичный список отзывов продавца содержит общее число отзывов, средний рейтинг и записи с пагинацией. Рейтинг вычисляется по сохраненным оценкам и не изменяется в сервисе авторизации.

Маршруты: `POST /api/v1/deals/{deal_id}/review` и `GET /api/v1/users/{seller_id}/reviews`.
